# ADR-0001: `type_` で始まる数値の列は、汎用の種類マスタ `trend_system_type` で名称を扱う

> **遡及作成(2026-10-08)**: 本ADRは、決定の後に、設計書と計画書の記述から書き起こした。仕様の本体は、設計書に有る(ここには書き写さない)。ここには、設計書と計画書に書かれた、判断の理由と、採らなかった案だけを記す。出典で確認できない点は「要確認」と記す。

## ステータス

提案中

## 背景・課題

保有銘柄のトレンドは、`trend.daily_trend` に、文字(`up` / `down` / `flat` / NULL)をそのまま持っていた。種類の意味を各テーブルの列に文字で持つと、種類が増えたとき(別の列にも種類が要るとき)に、意味の置き場所が列ごとに散らばる(設計書10「実装背景」)。

## 決定

- 種類の意味は、1つの表 `trend_system_type`(`type_column` / `type_name` / `type_value`)に集める
- 種類を持つ列は、`type_` で始まる数値の列(`SmallInteger`、NOT NULL、既定0。0は none)にし、名称は、マスタとの JOIN(1回の問い合わせ)で引く。JOIN と名称付けは、共通部品 `trend_system_type_service` に置く
- 最初の使い手は、保有銘柄のトレンド(`daily_trend` → `type_daily_trend`)。API と画面は、数値でなく、名称(文字)を扱う
- 一致する行が無い、またはマスタが空のときも、一覧は表示する(名前は `none`)
- 他テーブルへの外部キー制約は付けない(このプロジェクトの方針。計画書 Task 6 の Global Constraints)

仕様の詳細: [設計書 10-trend-type-master.md](../design/10-trend-type-master.md)。実施の手順: [計画書](../superpowers/plans/2026-10-01-AIDDS-9-feature-improvement-202610-01.md) の Task 6(AIDDS-10)。

## 検討した代替案

- **文字を、各テーブルの列に、そのまま持つ(従来)**: 採らず。意味の置き場所が列ごとに散らばるため(設計書10「実装背景」)
- そのほかの案(種類の名称を、コード内の定数だけで持つ案など)は、記録に無い。要確認

## 影響・トレードオフ

- マスタを、実際に JOIN して使うため、一覧の取得は、マスタに依存する(一致する行が無いときの `none` で、表示は守る)
- 列名と型が変わるため、既存のDBは作り直す(マイグレーション機構が無い。計画書 Task 6 の確認済み7)
- 今回は、保有銘柄のトレンド以外の `type_` 列は、追加していない。足し方は、設計書10「別の `type_` 列を足すとき」に書かれている
- 種類を増やす画面や、API での編集は、持たない(設計書10「対象外」)
