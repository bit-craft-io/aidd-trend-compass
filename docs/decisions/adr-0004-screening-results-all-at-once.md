# ADR-0004: 発掘の結果 API は、全件を返し、`none` の除外とページ分けは、フロントで行う

> **遡及作成(2026-10-08)**: 本ADRは、決定の後に、設計書と計画書の記述から書き起こした。仕様の本体は、設計書に有る(ここには書き写さない)。出典で確認できない点は「要確認」と記す。

## ステータス

提案中

## 背景・課題

発掘の一覧のトレンドを、保有一覧と同じ形(種類マスタの名前。ADR-0001・0003)にそろえる(AIDDS-17)。このとき、結果 API の項目名と、`none` の銘柄の扱いと、ページ分けの置き場所を、決める必要があった。

## 決定

- 項目名は、`daily_trend` をやめ、保有一覧と同じ `type_daily_trend`(`none` / `up` / `down` / `flat`)にする。理由: マスタの参照が同じため。`daily_trend` という名前にすると、マスタに、別の種類の列ができてしまう(設計書09の末尾の節)
- 判定できないときも、`null` でなく、`none` を返す
- サーバーは、ページに分けず、条件に合う全件を返す(`page`・`page_size` を廃止)
- フロントが、`none` の銘柄を除き(シグナルの条件を1つも選んでいないときを除く)、1ページ20件に分ける。件数とページ数は、除いたあとの件数で数える
- 発掘のトレンドは、DB に列を足さず、表示のときに、保存済みの日足から判定する(従来どおり)

仕様の詳細: [設計書 09](../design/09-trend-direction-and-market-colors.md)の末尾の節。確認の記録: [計画書](../superpowers/plans/2026-10-01-AIDDS-9-feature-improvement-202610-01.md) の「追記: AIDDS-17・AIDDS-18 の確認してほしい点」の3〜5(確認済み)。

## 検討した代替案

- **サーバーで、ページ分けを続ける(従来)**: 採らず。ただし、理由は、記録に明記されていない。`none` を除いたあとの件数で、ページ分けするためと読めるが、これは推測(要確認)
- **発掘の項目名を、`daily_trend` のままにする**: 採らず。上のとおり、マスタに別の種類の列ができてしまうため。なお、AIDDS-10 の時点では、「当面は、このままにする」としていた(計画書 同上、確認済み5)。AIDDS-17 で、そろえた

## 影響・トレードオフ

- 条件なしで検索すると、全候補(設計書では約1600。今の `JQUANTS_MAX_STOCKS` の既定は10)のトレンドを、1回の取得で計算する。実際の費用は、測っていない。Task 7 の実機確認で、候補を1000件入れて、応答時間を測る計画だった。結果は、記録に無い(要確認)。遅ければ、見直す兆候
- API が、`none` の除外を、していない。API を使う別のクライアントが現れたら、除外を、それぞれが行う必要がある
- API の `total` は、除く前の件数。画面は、使わない
